## 0. 一页结论

1. **市场窗口是真实的，而且正好对准这个产品。** 2026 上半年入境外国人 2291.4 万人次（同比 +20.4%），其中**免签入境占 77.7%**。也就是说，"我能不能免签进中国"这个问题，覆盖了四分之三的入境需求——这正是本站首页的第一功能。
2. **内容不再是壁垒，"可信"才是。** 同类站点（travelchinahub、travelhubchina、chinatravelatlas、roamchinatravel 等）已经批量铺满"visa free countries 2026"这类清单页，且多为 AI 批量生成、更新日期不可验证。本站已有的"最后核实日期 + 官方来源 + 变更日志 + 受保护数据审批"制度，是这个赛道里**唯一无法被批量复制的东西**。
3. **变现不该从广告开始，应从"数据资产"开始。** 展示广告在旅游类目 RPM 只有 1.5-5 美元（美区加权 12-20 美元），是兜底而非主线；affiliate 的天花板由流量决定；真正高毛利的是把这份可审计的政策数据做成 API / 嵌入组件，卖给旅行社、留学中介、外籍 HR、航司地服。
4. **当前最该修的不是功能，是三处"制度空转"**：受保护数据的守门员盯错了文件、全站"最后核实日期"是一个 5 个月没变的硬编码、检查器全绿但没有任何一条真浏览器验证。
5. **架构上不要重写。** 现有选型（静态 + 生成器 + 检查器）是对的，需要补的是"模板单一来源、CI 门禁、真浏览器测试、去 Google 依赖"四件事，全部是增量。

### 竞争格局的三个事实

1. **同质化严重。** 头部竞品页面结构高度一致：签证清单 + 支付 + eSIM + 高铁 + 行程模板。这些内容 AI 一天能生成 50 页。
2. **信任普遍不可验证。** 竞品普遍标 "Updated Oct 8" 却不给官方链接、不给核实方法、不给变更历史。
3. **政策变动频繁 = 持续的内容更新成本。** 免签名单、240h 口岸、停留区域近两年反复调整。对批量内容站这是负担，对**有结构化数据 + 生成器**的本站这是护城河：政策一变，改一个数组，全站 58 页同步刷新。

### 因此本站的正确位置

> 不是"又一个中国旅游指南"，而&#x662F;**"外国人入境中国的可信决策层"**：  
> 你能查到"我这种情况到底能不能进、能待几天、从哪个口岸、依据哪条官方规定、这条规定什么时候核实的"。

这个定位同时决定了产品（资格检查器）、内容（变更日志）、架构（数据单一真相源）和变现（数据授权 / 白标组件）。

## 2. 业务方向：三层收入结构

不要平铺五个收入来源，按"依赖关系"分三层，一层养一层：

```
第一层 流量层   affiliate（机票/酒店/火车/eSIM/保险）      ← 依赖自然流量
      ↓ 把访客变成可触达的人
第二层 关系层   政策变更邮件订阅                            ← 依赖结构化数据 + 变更日志
      ↓ 证明数据可被外部系统消费
第三层 资产层   政策数据 API / 白标 widget / B2B 监控订阅    ← 依赖可审计的数据资产
```

**为什么是这个顺序：** affiliate 是唯一"今天就能挂上"的收入，但它受 EPC（每次点击收益）和流量双重限制，天花板低；邮件订阅把"一次性搜索流量"变成"可反复触达的资产"，同一批人的 aff 转化通常显著高于站内；而 B2B 是唯一不看流量、看数据质量的收入，毛利最高，也最难被抄——因为对手没有那套审批制度。

### 各阶段的战略目标

| 阶段     | 时间     | 一句话目标                                     | 关键结果                          |
| ------ | ------ | ----------------------------------------- | ----------------------------- |
| 阶段一 立信 | 0-2 月  | 让"可信"变成用户能看见的东西                           | 每页有真实核实日期；变更有公开日志；Google 依赖清零 |
| 阶段二 立量 | 2-5 月  | 把 55 国 × 口岸 × 路线扩到 150 页，且每页有"下一步"        | 自然流量 3 倍；工具完成率 >40%           |
| 阶段三 立钱 | 4-9 月  | affiliate 铺满 + 订阅破 5,000 + B2B 拿到 2 个付费客户 | 月收入 $500 → $2,000             |
| 阶段四 立品 | 9-18 月 | 从"站点"变成"可被嵌入的基础设施"                        | 10 个 B2B 客户；API 月调用 100 万+    |

## 3. 系统架构意见（附理由）

> 说明：每条给"是什么 / 为什么 / 怎么做 / 风险"。理由部分用非技术语言写，可直接拿去判断要不要做。

### A1. 页面骨架必须单一来源（当前最急的架构债）

- **是什么**：现在 57 个页面的导航和页脚是各自手写的，而且有两套样式（visa 页用 `lw-nav`，life/legal/about 用 `vm-topbar`）。生成器里其实已经有 `layout()` 函数，但手写页没走它。
- **为什么**：改一次导航要改 57 个文件，漏一个就出现"网站上两版导航"。这不是洁癖问题——**它让你不敢改导航，而导航决定用户能不能找到变现页面**。
- **怎么做**：先把 5 个高频页（首页、`/visa/`、240h 页、`/life/pay`、`/about`）迁到 `layout()`，验证无视觉回归后批量迁移。旧样式保留一个版本周期。
- **风险**：批量迁移会引入链接/锚点错误——`check-site.js` 已能抓内链失效，正好当保险。

### A2. 内容与展示分离（正文进数据，不进代码）

- **是什么**：现在页面正文是 JS 字符串拼接（`generate-seo-pages.js` 有 1140 行模板）。改一句文案 = 改代码。
- **为什么**：分离后，改内容只是改数据文件，非技术也能做；同一份数据还能一次输出英文页、中文页、API JSON。**B2B 变现的前提就是"内容已经是结构化数据"，否则卖不出去。**
- **怎么做**：新增 `content/visa/*.json`（每页：标题、摘要、要点、FAQ、来源、适用国家）。新页先走新结构，老页按流量热度渐进迁移。不要一次性全迁。
- **风险**：迁移期两套来源并存 —— 用"页面头注释标记 legacy / new"避免混乱。

### A3. 加 CI 门禁 + PR 预览

- **是什么**：`.github/workflows/ci.yml`：PR 时自动跑 `npm ci && npm run build`（内含 8 类检查），Cloudflare Pages 自动出预览链接。
- **为什么**：现在的检查器只在本地跑，等于"自己给自己判卷"。装到 CI 后，任何改动必须先过检查才能合并——**网站有了刹车，才敢加大改动频率**。
- **怎么做**：CI 跑 build + check；`monitor:live` 用 schedule 每天跑一次，失败发通知。
- **风险**：几乎无。CI 分钟数在这个体量下免费额度足够。

### A4. 补 10 条真浏览器测试（E2E）

- **是什么**：Playwright 跑：首页 4 个 tab 切换、停留期计算、汇率换算、时区换算、3 个国家页、1 个 240h 页面。
- **为什么**：现有检查只证明"字符串在文件里"，不证明"点下去算得对"。**签证计算差一天，用户可能被拒绝入境——这是会直接毁掉品牌的错误，只有真跑浏览器才抓得到。**
- **怎么做**：`tests/e2e/` + 固定 10 条断言（如入境 2026-01-01 + 30 天 → 最晚离境 2026-01-30）。
- **风险**：维护成本；用"少而稳"的 10 条，不要追求覆盖率。

### A5. 去 Google 依赖（这不是性能优化，是"能不能看见用户"）

- **是什么**：11 个页面从 `fonts.googleapis.com` 加载 Inter；统计走 `googletagmanager.com`。
- **为什么**：你的用户正是在中国境内的外国人。这两个域名在中国大陆通常不可用 → 字体退化、统计**整段丢失**。你现在看到的 GA 数据，很可能系统性低估了中国境内的真实用户，而这恰恰是核心人群。
- **怎么做**：字体自托管（Inter 子集 woff2，或直接退回 `system-ui` 字体栈，零请求）；统计**新增** Cloudflare Web Analytics，与 GA **长期并存**。
- **分工（重要）**：Cloudflare 回答「来了多少人」——无 cookie、中国大陆可达、覆盖全量；GA 回答「他们在页面上做了什么」——事件、漏斗、归因。**两者不是重复，是互补，不需要对账。**
- **风险**：唯一成本是要记住两个后台各看什么，属一次性认知成本。**只有**满足以下任一条件才考虑摘掉 GA：① 不再需要事件级分析；② GA 覆盖比例低到没有分析价值；③ 面向欧盟的 cookie 合规压力。否则并存就是合理的长期状态。

### A6. "最后核实日期"必须是数据，不能是常量

- **是什么**：现在 `shared/nav-data.js` 里 `LWDefaultLastVerified = '2026-05-27'`，全站共用，已经 5 个月没变。
- **为什么**：可信度是这个项目唯一的护城河。一旦"最后核实"是装饰性的，整套审批制度就变成表演——而且用户/媒体一旦发现，信任是不可逆的。**更重要的是：只有按数据集记录核实时间，才能对外提供"变更通知"这个付费产品。**
- **怎么做**：每个受保护数组加 `verifiedAt` 与 `sources`；页面渲染取该数组的 `verifiedAt`；`sitemap.xml` 的 `lastmod` 从同一字段派生（现在 `generate-seo-pages.js` 里 `LASTMOD` 是硬编码 `2026-05-27`）。
- **风险**：需要一次真实核查动作。宁可写"2026-10-22 复核，未变更"，也不要沿用旧日期。

### A7. 需要后端时，用 Cloudflare Workers 同域 `/api/*`

- **是什么**：订阅、汇率缓存、变更提醒、对外 API，全部放 Workers，路径挂 `laowaitown.com/api/*`。
- **为什么**：这些功能必须有服务端。选 Workers 的理由是：与现有部署同一平台、**同域名（免跨域、免额外证书）**、免费额度足够、不用维护服务器。对单人维护的站，运维成本比性能重要得多。
- **怎么做**：`functions/api/subscribe.js`、`functions/api/visa.js`，`wrangler.jsonc` 保持不变（Pages 自动识别 `functions/`）。
- **风险**：引入 KV/D1 后出现"状态"，需要备份策略；初期只用 KV，不要上复杂数据库。

### A8. 汇率双源 + 缓存

- **是什么**：目前只依赖 `open.er-api.com` 一个外部源，失败即工具失效。
- **为什么**：首页三个工具里，汇率是唯一有外部依赖的。它挂了，用户看到的是"这个站坏了"，而你可能几天都不知道。
- **怎么做**：Worker 缓存 1 小时；主源失败切备用源；界面显示"汇率更新于 xx:xx"，失败时降级到内置 `USD_RATES` 并明确标注"离线参考值"。
- **风险**：备用源格式不同，需要归一化层。

### A9. 监控接定时任务（已有代码，没人跑）

- **是什么**：`scripts/monitor-live.js` 会把 sitemap 里 58 条 URL 全测一遍，但现在只能手工跑。
- **为什么**：一个没人执行的监控等于没有。接到每日定时 + 失败通知，才能第一时间发现"某页 404 / 证书过期 / 部署失败"。
- **怎么做**：GitHub Actions `schedule` 每天 08:00（北京时间）+ 失败时邮件/IM 通知。

### A10. 明确"不做"的重构

- **不做**：不用 Next.js / React / Astro 重写；不引入 CMS；不上数据库做内容管理。
- **为什么**：58 个页面已被搜索引擎收录，重写会损失排名、丢掉现有检查体系、把维护面从"几个 JS 文件"扩大到"一套框架 + 构建 + 依赖"。**收益不在框架，在内容和信任。** 静态站真正的优势是"零运维 + 极快 + 极便宜"，不要主动放弃。

### 架构改造的优先级排序（理由）

1. **A1 模板 + A3 CI**：先降"改动成本"，后面所有事都变快。
2. **A6 核实日期 + A5 去 Google**：直接决定"可信"和"看得见用户"，属于收入前提。
3. **A4 E2E + A7 Workers**：前者保命，后者打开订阅/API 的门。
4. **A2 内容结构化**：为 B2B 铺路，但可以渐进，不阻塞变现。
5. **A8/A9**：低成本高收益，随手做。

**任务流的依赖关系（为什么这个顺序）：**  
变现建立在信任上，所以 Phase 1 必须先于 Phase 3；模板统一降低后续所有改动成本，所以 Phase 2 在 Phase 3 前；内容结构化是 API 的前提，因此 Phase 2.2 要在 Phase 4.1 前。**不要跳过 Phase 0**——守门员失效期间任何一次数据事故，都会把前面积累的信任一次性清零。

### 第 2 步：政策变更邮件订阅（第 3-8 周）——真正的资产

**价值主张（只有这个站讲得出来）**
> "你关注的免签政策变了，我会告诉你。" —— 因为你有结构化数据 + 变更日志，能在政策变动当天精准通知"受影响的那批国籍"。

**为什么这一步比加 50 个 SEO 页更重要：** 搜索流量是一次性的，订阅是可反复触达的。同一批人，邮件里的 aff 转化通常显著高于站内；而且订阅数是可以拿去谈 B2B 与赞助的硬资产。

**落地**
- 技术：`functions/api/subscribe.js`（Workers）+ Resend 或 Buttondown（免费额度起步）；双确认（double opt-in）；只存邮箱 + 关注的国家/话题，不存多余个人信息。
- 入口：`/visa/*` 结论卡下方 + `/changelog` 页 + 240h 页；文案强调"只在影响你的时候发"。
- 触发：数据文件 `verifiedAt`/`changLog` 更新时，按影响的国籍段群发。
- 合规：明确退订、隐私说明；邮件主题不得暗示官方身份（本站是独立站点）。

**指标与预期**
- 订阅转化率：政策页 1.5-3%（高于普通内容页）
- 3 个月目标 1,000 订阅；6 个月 5,000
- 邮件打开率预期 35-50%（低频高相关），远高于行业 20%
- 变现路径：前期只做 aff 与信任；5,000 订阅后可卖"单期赞助"（每千订阅约 $30-80）

### 第 3 步：B2B 数据与嵌入组件（第 3-6 月）——最高毛利

**产品形态（三档，先做最小可用）**

| 档位 | 内容 | 定价（建议） | 目标客户 |
|---|---|---|---|
| Starter | REST API，10 万次/月，返回资格结论 + 来源 + 核实日期 | $99/月 | 留学中介、小型旅行社 |
| White-label | `widget.js` 嵌入自己网站，可换色/去品牌，含 API | $299/月 | 旅行社官网、OTA、酒店集团 |
| Enterprise | 定制 + SLA + 政策变更实时推送 + 专属核查 | $999/月起 | 航司地服、大型 OTA、外籍 HR SaaS |

**客户为什么付钱（这是定价的底气）**
他们最怕的不是"不知道政策"，是"说错了导致客人被拒绝入境"。一单投诉的赔偿与口碑损失，远高于 $99/月。你的卖点不是"信息多"，是**"每条结论都能追溯到官方来源和核实日期"**——这正是竞品拿不出的东西。

**落地顺序**
1. 先把 4 个受保护数组抽成纯数据模块（无 DOM 依赖），使其能在 Worker 里直接引用。
2. `GET /api/visa?passport=US&port=PVG&days=3` 返回 `{eligible, policy, maxStay, sources[], verifiedAt}`。
3. `widget.js` 渲染一个 60 行以内的资格检查组件，`?theme=#0ea5e9` 换主色。
4. 定价页 + 自助申请 key（手工发 key 起步即可）。
5. 拿 2 个种子客户换反馈，允许前 3 个月半价。

**预期效果**
- 3 个 Starter + 1 个 White-label ≈ $596/月（约 ¥4,300）
- 10 个客户 ≈ $1,500-2,500/月，且**与流量无关**——这是收入结构的质变
- 隐性收益：B2B 客户会主动指出数据错误，等于免费获得核查力量

### 第 4 步：赞助与联名（第 6-12 月）

- **单页赞助**：eSIM、保险、支付工具在 `/life/*` 与 240h 页的固定位置，按月计费（按 3-8 万 PV 量级，建议 $200-800/月/位）。
- **邮件赞助**：$30-80 / 千订阅 / 期，5,000 订阅 ≈ $150-400/期。
- **数据联名**：与航司/签证服务商联合发布"季度入境政策报告"，换外链与品牌背书——这是低成本的权威建设。
- **不建议做 AdSense 主线**：旅游类 RPM 1.5-5 美元，12,000 PV 只有 $18-60/月，却要付出速度与观感代价。可作为长尾兜底，但不要为它牺牲版面。

### 第 5 步：付费服务（第 12 月后，验证后再说）

- **入境资格人工复核**：$19-39/次，30 分钟内出结论 + 依据。用兼职顾问交付，先限量 10 单验证需求真伪与交付成本。
- **B2B 政策监控告警**：$49/月起，政策变动即时推送 + 影响面分析（"这次变更影响这 12 个国籍"）。
- **判断标准**：如果 10 单里你能做完 8 单且客户满意度高，才值得产品化；否则停在 API 层，不要碰服务交付。

## 7. 风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 政策说错导致用户被拒入境 | 品牌毁灭性 | 保持"独立站点 + 不作为法律意见"免责；每条结论带来源与核实日期；关键数据双人复核 |
| 联盟链接未披露 | 合规风险（FTC/广告法） | 统一披露组件 + `rel="sponsored"` |
| 流量过度依赖 Google | 算法更新即断崖 | 邮件订阅 + RSS + 少量高质量社媒；B2B 收入去流量化 |
| 政策突变导致批量页面失效 | 维护成本激增 | 数据单一真相源 + 生成器重跑；这正是现有架构的优势 |
| 竞品批量 AI 内容压价 | aff 单价下行 | 不打价格战，转向"可信 + 工具 + B2B"三处差异化 |
| 单人维护导致制度荒废 | 缓慢腐烂 | CI 门禁 + 核实日期可见化，让"偷懒"立刻可见 |
